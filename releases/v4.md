## 这一版做了什么

目录数据从「名字 + 一句描述」升级为**可精确检索的数据**，并第一次把契约写成机器可校验的 schema。

- **`version`: 3 → 4**，15 个条目全部补齐：`tags`（受控词表，34 个小写 ASCII 词）、`aliases`（中英别名）、`homepage`（https）、`added_at`。原有字段零改动，**纯增量**。
- 新增 [`schema/`](../schema/README.md)：`index.schema.json` + `skill.schema.json`（draft-07），含 v4 条件契约（`version >= 4` ⇒ 每条目必须有 `tags`/`aliases`/`added_at`）。
- 新增 `scripts/check_schema.py`：jsonschema 严格校验 + **schema 自证**（14 个正/负样本必须按预期判定）+ **防漂移**（`validate.py` 常量 ⇄ schema 枚举严格一致）。
- 新增 `scripts/selftest.py`：43 条规则自测，**每条规则配一个负样本**。它是「CI 绿灯 = 数据合格」这个等式的证据，而不是口号。
- 新增 [`review-log/`](../review-log/README.md)：审核裁决留痕（append-only），CI 以 `--strict` 校验留痕与 `index.json` 双向一致。
- CI 加固：actions 固定到 commit SHA；新增 schema 校验、留痕校验、死链探测、自测四步 —— 以 [`ci/validate-workflow.patch`](../ci/README.md) 交付（当前 GitHub 连接无 `workflows` 权限，无法直接提交 workflow 改动；机制本身已入库，本地随时可跑）。
- **修复**：危险指令扫描正则漏检 `rm -rf ~` / `rm -rf /` / `rm -rf $HOME`（`\b` 收尾既不是单词字符也不该用），同时误报 `rm -rf /tmp/build`。两类问题已一并修掉。

## ⚠️ 已知阻断问题（主仓库侧必须处理）

两个客户端都用 **SHA256 钉扎**远程内容，而远程 URL 指向可变的 `raw.githubusercontent.com/.../main/index.json` —— 后果是**任何目录更新都会被判为「源可能被篡改」而拒绝**，客户端会永远停在旧版本。v4 之前这个问题被 v3 掩盖（内容一直没变），**v4 是第一次真正踩到它**。

修复方向（主仓库改动，详见 [CHANGELOG](../CHANGELOG.md)）：

1. 改为「上游 `version` 单调递增 ⇒ 接受更新并刷新哈希；同版本内容变化才判可疑」；
2. 改为 **tag 固定拉取** `@v<version>`，jsDelivr 主源 + `raw.githubusercontent.com` 备用源；
3. Python 侧透传 `tags`/`aliases`；JS 侧把 `aliases` 并入词法字段。


## 升级须知（安装者）

`index.json` 的消费只需遵守一条：**忽略不认识的字段**。若你的客户端在 `version` 变大后拒绝更新，那是因为哈希钉扎策略，先升级主仓库的同步逻辑（见上）。
